# 19장 로깅: EFK (Elasticsearch·Fluentd·Kibana) (쪽수 확인 필요)

## 명령
- 빌드 `cd ~/MSA/Chapter19 && ./gradlew build`. 코드는 18장과 동일, 쿠버네티스 파일만 추가(`kubernetes/efk`, `helm/environments/logging`)
- Fluentd 이미지: `docker build -t hands-on/fluentd:v1 kubernetes/efk` 후 minikube에 `image load`
- 설치: `kubectl create namespace logging`, `helm install logging-efk helm/environments/logging -n logging`, `kubectl apply -f efk/fluentd-hands-on-configmap.yml -f efk/fluentd-ds.yml`
- 확인: ES `port-forward svc/elasticsearch -n logging 19200:9200` 후 `_cat/indices`, `_search`. Kibana 저장 객체는 `ndjson`을 `/api/saved_objects/_import`로 가져옴

## [Boot4] 변경
- 없음. 코드·차트 변경 없이 18장 그대로. Fluentd 정규식이 Boot 4 로그(`[서비스,traceId,spanId]`, `include-application-name: false`)와 그대로 맞는지 실제 문서로 확인

## 복습 포인트
- Fluentd(DaemonSet)가 컨테이너 로그를 수집해 태그를 바꾸고(`rewrite_tag_filter`) 정규식으로 `spring.service/trace/span/class/level` 필드를 추출, `logstash-*` 인덱스에 저장
- 스택 트레이스는 `detect_exceptions`가 여러 줄을 한 문서로 묶음(114줄 문서 확인). 묶인 문서에는 시작 줄의 파싱 필드가 붙지 않는다
- Fluentd가 ES보다 먼저 뜨면 `Connection refused` 후 지수 백오프로 재시도해 수 분 뒤 인덱스가 생긴다
- 결과: 빌드 통과, minikube(Istio minimal)에서 서비스 5개 로그 파싱(192건), Kibana 7.17.28 green, 저장 객체 3개 가져오기 성공
- 검증 범위: Istio 게이트웨이·Jaeger·cert-manager는 설치하지 않음. 앱 시작 직후 `recommendation`이 MongoDB 대기 후 1회 재시작(시작 순서 경합)
